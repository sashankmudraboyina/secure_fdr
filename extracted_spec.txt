1. Product vision and problem definition
AICTE needs a centralized mechanism to maintain institution-wise and instrument-wise records of security deposits and FDRs, review submitted documents, obtain independent verification wherever available, monitor maturity and validity, track replacement instruments, coordinate release/refund requests and preserve a traceable administrative history.
SecureFDR 360 should move beyond simple file storage. The prototype demonstrates four connected ideas: (1) a Digital Deposit Passport for each instrument, (2) independent bank attestations through a sandbox, (3) a permissioned blockchain trust ledger for tamper-evident evidence events, and (4) a policy-aware release workflow that retains human approval authority.
1.1 Product principles
Bank facts and institution declarations must remain separate. OCR output is extracted evidence, not proof of authenticity.
Blockchain records evidence provenance and lifecycle events; it does not independently prove that an uploaded claim is true.
No sensitive document, account number, personal identifier or full FDR number should be written to public/shared ledger state.
AI may extract, compare, summarize and prioritize. Deterministic backend rules must govern required fields, state transitions and release gates.
Final approval or rejection remains with the authorized AICTE official. No autonomous AI release decision.
All prototype data must be synthetic and visibly marked as demo data.
Any AICTE regulatory rule values supplied as seed data must be labelled illustrative until confirmed by AICTE.
1.2 Prototype boundaries
In scope for SIH prototype

Full role-based web portal; instrument repository; PDF/image upload; OCR and field extraction; discrepancy detection; bank verification simulator; Fabric local test network; immutable lifecycle events; replacement lineage; duplicate detection; configurable demo policy; release workflow; alerts; dashboard; audit explorer; tests and README.
Live bank APIs; actual AICTE portal integration; real PGRC/Vigilance connectivity; official DSC infrastructure; real DigiLocker integration; production bank keys; production cloud deployment; legal determination of release eligibility; actual fund transfer.
Non-negotiable terminology
In the UI use “Bank Sandbox — simulated” for test attestations. Use “Bank confirmed” only for an authenticated bank response within the prototype’s controlled test network, and always display “Synthetic demo environment”. Do not imply a live bank connection.

3. Core user journeys and business workflows
3.1 New FDR submission
1. Institution user signs in and opens “Add Financial Instrument”.
2. User selects the security-deposit obligation (or creates a draft obligation reference if demo rules allow), enters declared details and uploads an FDR PDF or image.
3. Backend validates file type/size, stores the original securely, calculates SHA-256, creates a document record and creates a unique instrument ID such as AICTE-FDR-2026-000184.
4. Document service extracts text from searchable PDF first; if no useful text exists, it runs OCR. It returns extracted fields and confidence values.
5. Comparison service checks institution-declared values against extracted values and generates discrepancy records.
6. Duplicate service generates a privacy-preserving HMAC fingerprint from normalized issuing bank code + FDR reference + instrument issue date (configurable), and checks if it already exists.
7. Instrument enters SUBMITTED or NEEDS_CLARIFICATION state. It is not marked bank verified.
8. Backend records an instrument-created event and document hash in the ledger adapter; when Fabric is connected, the event must be committed to Fabric.
3.2 Bank verification
1. AICTE reviewer clicks “Request bank verification”. The backend creates a bank verification request with a unique request ID and selected fields to confirm.
2. Bank verifier signs in to the Bank Sandbox and views only requests for its bank.
3. Bank verifier inspects the synthetic bank record and selects a result: ACTIVE_AND_LIEN_CONFIRMED, ACTIVE_LIEN_MISMATCH, NOT_FOUND, CLOSED_OR_ENCASHED, MATURITY_MISMATCH or NEEDS_MANUAL_REVIEW.
4. Bank sandbox creates a response payload containing request ID, instrument reference, confirmed fields, status, verified_at, nonce and key_id. It signs canonical JSON using a development private key.
5. Backend verifies the signature against the registered demo public key, validates nonce and request freshness, compares confirmed values with submitted/extracted values and saves the attestation.
6. Backend sends the attestation digest and status event to Fabric through the Gateway service. UI displays “Bank Sandbox — simulated” even though the signature and ledger transaction are technically validated.
3.3 Discrepancy handling
A discrepancy is a review flag, not an accusation of fraud. Each discrepancy must store field name, source A, source B, severity, explanation, current status (OPEN / UNDER_REVIEW / RESOLVED / ACCEPTED_WITH_REASON) and resolution actor. Never auto-reject an institution solely because OCR confidence is low.
3.4 Maturity and status monitoring
A scheduled job checks instrument maturity dates daily. Prototype reminder offsets should be configurable (default demo values: 90, 60, 30 and 7 days before maturity, plus overdue). Do not hardcode these as official AICTE timelines. On each alert, create an in-app notification and a dashboard item. If an authenticated bank sandbox event reports closure/encashment or lien change, create a high-priority discrepancy and append a ledger event.
3.5 Replacement instrument
1. Institution opens an existing instrument and selects “Submit replacement”.
2. New instrument goes through the same upload, OCR, comparison and bank-verification flow.
3. After reviewer confirmation, create a relationship record from old instrument to new instrument with reason and supporting evidence.
4. Old instrument becomes SUPERSEDED only after the configured acceptance gate; never delete it or erase its history.
5. Prevent circular replacement chains and prevent more than one current instrument for the same deposit obligation, unless the configured policy explicitly supports multiple instruments.
3.6 Release/refund request
1. Institution selects an eligible instrument and starts a release request, uploads required supporting documents and provides a reason.
2. Policy engine evaluates configured demo rules and outputs PASS / FAIL / NEEDS_HUMAN_REVIEW per check, including a reason and policy version.
3. AICTE reviewer reviews the documents and creates required clearance tasks (for example PGRC, Vigilance, Approval Bureau or other configurable authority). The exact list must be configurable, not hardcoded as universally applicable.
4. Clearance owners complete tasks with a result, note and evidence attachment. Each task is attributable and timestamped.
5. When all mandatory clearances are complete, request a fresh bank status verification. The release process must stop if the bank reports closed/encashed, lien mismatch, not found or stale/unknown status.
6. If all configured gates pass, case enters READY_FOR_APPROVAL. A separate AICTE approver reviews and explicitly approves or rejects with a reason.
7. Approval records release authorization only. Do not simulate transfer of money. Mark COMPLETED only after an authorized completion/closure action is recorded.
8. Write relevant lifecycle, clearance and approval events to the ledger and append-only audit log.

4.3 Policy engine design
Keep policy rules as versioned JSON/relational records with rule_code, title, applicable institution category, effective_from, effective_to, version, enabled flag and rule_parameters JSON.
For the prototype, seed clearly illustrative rules only. Do not hardcode values or claim they are official AICTE rules.
Each evaluation must save the exact policy version, inputs snapshot hash, individual checks, result, explanation and evaluation timestamp.
Rule engine output must be explainable: “FAIL — bank lien is not confirmed” rather than only a numeric score.
An override requires a designated authority, a mandatory reason and an audit event. Do not permit silent overrides.
If a case cannot be evaluated confidently, return NEEDS_HUMAN_REVIEW, not PASS.

8.1 Important data rules
Instrument amount must be stored as numeric/Decimal, not float. Store currency code (default INR).
Normalize FDR reference for comparison but preserve the original submitted reference in protected off-chain storage.
Fingerprint must be generated server-side with HMAC-SHA-256 using a secret from environment variables. Do not expose the HMAC secret to frontend or write raw FDR reference to ledger.
Document SHA-256 is calculated on original bytes at upload. Recalculate on download/verification where required.
Each bank attestation must preserve the raw signed response and signature verification outcome off-chain; the ledger stores a digest/reference, not all banking information.
All date-based jobs must use a consistent timezone setting (UTC in storage; display user local/Asia-Kolkata for this India prototype).
Use soft delete only for operational master data if necessary. Do not delete financial evidence, audit records or ledger event references.

10. Document intelligence and discrepancy detection
10.1 File handling
Allow only PDF, JPG and PNG for the prototype. Reject executable, HTML, SVG and unknown MIME types.
Prototype size limit: configurable, default 10 MB per file. Validate extension, MIME type and file signature/magic bytes.
Generate random storage keys; never trust user-supplied path or filename for filesystem path creation.
Store outside frontend static directory. Serve through authenticated API endpoint after permission check.
Calculate SHA-256 at upload and store it with file metadata.
If feasible, add antivirus scanning hook interface; if scanner is unavailable locally, document this as a production requirement.
10.2 Extraction strategy
Step
Implementation
1. Detect document
Read file type, pages and size. Extract embedded text with PyMuPDF for PDF.
2. OCR fallback
If extracted text is empty/too short or page is image-only, render pages to images and use Tesseract or PaddleOCR.
3. Normalize
Normalize whitespace, dates, currency formatting, IFSC-like codes and FDR reference tokens. Preserve raw text separately.
4. Extract fields
Regex/rule-based extractors for bank name, IFSC/branch, FDR number, amount, issue date, maturity date, depositor, beneficiary/lien. Build per-field confidence.
5. Human review
Display editable extracted fields beside the original document. Mark low-confidence fields “Needs review”.
6. Compare
Compare declared vs extracted values; later compare both against bank-attested values.
7. Save provenance
Store extractor type/version, extraction timestamp and source document id.

11. Blockchain trust ledger implementation
11.1 What goes on-chain vs off-chain
On-chain (minimal evidence)
Off-chain (private operational data)
Opaque instrument UUID; HMAC fingerprint token; document SHA-256; attestation digest; event type; status code; organization/MSP identity; Fabric transaction ID; timestamp; replacement relationship IDs; policy version reference; clearance/approval evidence digest.
Original FDR PDF/image; full FDR number; account details; depositor personal data; bank response JSON; affidavits; emails; notes; detailed financial data; identity documents; extracted OCR text; private contact information.
Privacy rule
Do not put raw FDR numbers, bank account numbers, PAN, Aadhaar, depositor names, full documents or complete bank-response payloads on the ledger. A hash is a tamper-evidence mechanism, not a reason to publish sensitive source data.

11.4 Trust boundaries and limits
Fabric verifies network identity and transaction endorsement. It cannot independently verify that a bank operator entered a truthful statement. The bank must check its own records before signing.
For prototype, bank response is signed using a demo keypair and labelled synthetic. The public key is registered in demo configuration. Never use real bank credentials or keys.
FastAPI must validate the bank signature, nonce, request ID and freshness before asking the Gateway to record its digest. Fabric then records the evidence event.
The Gateway service must use separate organization credentials. Do not use a single all-powerful identity for both AICTE and BankOrg.
If Fabric is offline, the main app may use a development-only append-only hash-chain adapter to remain runnable, but UI must clearly show “LOCAL AUDIT FALLBACK — NOT BLOCKCHAIN”. The final SIH blockchain demo must run with Fabric and show a Fabric transaction ID.

The Node Gateway client API supports submit/evaluate transactions against a Gateway-enabled peer. Appendix A — Scope and prototype disclaimer
This is a software prototype specification for SIH demonstration. All institutions, users, FDR numbers, bank names, attestations, cryptographic keys, maturity dates, policy parameters and workflow outcomes used in demo data must be synthetic. A successful simulated bank attestation is not a real bank confirmation. A ledger transaction proves that an authenticated organization recorded an event under the prototype network; it does not independently prove the truth of underlying financial facts. A real deployment requires AICTE approval, applicable legal/policy validation, bank agreements, security assessment, privacy review, operational governance and production-grade identity/key management.
Final principle
SecureFDR 360 is successful when it can show the difference between (1) what the institution declared, (2) what the document appears to contain, (3) what the bank sandbox independently attested, and (4) what AICTE authorized after applying the configured rules. Preserve these four evidence layers in every major screen and workflow.
